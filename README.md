# Сбор и приоритизация общедоступных IoC

Тестовое задание для БКС на Python. `collect.py` собирает индикаторы из
**CINS Army, ThreatView и Blocklist.de**, нормализует их и сохраняет в локальную
SQLite. `ioc.py` выводит индикаторы по приоритету и экспортирует результаты.
**Все три источника доступны без регистрации и API-ключей.**

Совпадение — одинаковая пара **тип + нормализованное значение**.
Приоритет (`level`) рассчитывается по правилу ТЗ:

| Различных источников | Уровень |
| --- | --- |
| 3 и более | Critical |
| 2 | High |
| 1 | Medium |

## Быстрый запуск

Нужен **Python 3.10+**. Проект использует модули стандартной библиотеки Python,
включая `sqlite3` для работы с БД. Дополнительные Python-пакеты через `pip`
устанавливать не нужно. Сама библиотека SQLite обычно уже поставляется
вместе с Python.

Команды выполняются из каталога проекта. Основная команда запуска — `python`.
На Windows также можно использовать `py -3`, на Linux — `python3`.

Сбор настоящих данных — без ключей и настройки окружения:

```shell
python collect.py
python ioc.py --stats
python ioc.py --level critical
python ioc.py --level high
python ioc.py --level medium --limit 10
```

База создаётся автоматически в `data/iocs.sqlite3`.
Сетевой запуск требует доступа к сайтам источников. Для повторных проверок
логики есть демо без сети:

```shell
python collect.py --demo
python ioc.py --db data/demo.sqlite3 --level high
python ioc.py --db data/demo.sqlite3 --level medium
python ioc.py --db data/demo.sqlite3 --level critical
python ioc.py --db data/demo.sqlite3 --stats
```

Демо использует синтетические файлы в форматах настоящих источников:
**10 уникальных IoC: 1 Critical, 4 High, 5 Medium**.
Домены и IP документационные, хеши вымышлены. Вредоносные файлы не скачиваются,
переходы по собранным URL и DNS-запросы к индикаторам не выполняются.
Данные demo и live нельзя смешивать в одной БД.

## Почему выбраны эти три источника

**Выбор обоснован следующими критериями:** нужно было выбрать **3 бесплатных
открытых источника**, обеспечить широкое покрытие типов IoC и сохранить
пересечения по типам для демонстрации сопоставления и повышения приоритета.
Если типы во всех источниках полностью разные, каждый индикатор всегда будет
иметь уровень Medium.

Дополнительный критерий этой реализации — **удобство проверяющего**:
полный сетевой сбор запускается без регистрации, получения ключей, настройки
секретов и передачи личных учётных данных автора. Это осознанный компромисс
тестового задания, а не утверждение, что источники без ключей всегда лучше.
Под открытостью понимается публичная доступность выбранных выгрузок;
это не отменяет условия использования данных и ограничения частоты запросов.

| Источник | Импортируемые типы | Практическая задача | Пересечение |
| --- | --- | --- | --- |
| CINS Army | IPv4 | Поиск адресов с неблагоприятной репутацией по данным Sentinel IPS | IP с ThreatView и Blocklist.de |
| ThreatView | IPv4/IPv6, домены, MD5 | Сопоставление сетевых событий, DNS и хешей файлов со списками угроз | IP с CINS Army и Blocklist.de |
| Blocklist.de | IPv4/IPv6 | Поиск адресов, замеченных в атаках на серверные службы | IP с CINS Army и ThreatView |

В выбранных выгрузках представлены четыре типа: `ipv4`, `ipv6`, `domain`, `md5`.
Общий тип IP позволяет сопоставлять один индикатор во всех трёх источниках
и получать Critical. Домены и хеши ThreatView расширяют покрытие за пределы
IP-списков. Таким образом, пересечение типов выбрано намеренно для проверки
всех уровней приоритета, при этом сохраняется разнообразие индикаторов.
Отдельного фида фишинговых URL в этой конфигурации нет. Нормализатор также
поддерживает `url`, `ip_port`, `sha1`, `sha256` для дальнейшего расширения.

### CINS Army

Используется [публичный текстовый список IP](https://cinsscore.com/list/ci-badguys.txt)
от Sentinel IPS. По [описанию поставщика](https://cinsscore.com/#list), адреса
отбираются по неблагоприятной оценке Rogue Packet либо по срабатываниям
доверенных правил на нескольких сенсорах Sentinel. Публичная выборка
ограничена 15 000 адресами и загружается без регистрации и API-ключа.

Источник добавляет сетевые индикаторы на основе телеметрии IPS и общий
с двумя другими поставщиками тип IPv4. Это позволяет получать Critical
по совпадениям исходных значений без извлечения IP из URL или доменов.
Файл содержит только адреса: оценки, причины включения и даты наблюдений
отдельных IP в него не входят. Это ограниченная публичная выборка,
а не вся база репутации CINS.

### ThreatView

Используются три текстовые выгрузки одного поставщика:
[IP](https://threatview.io/Downloads/IP-High-Confidence-Feed.txt),
[домены](https://threatview.io/Downloads/DOMAIN-High-Confidence-Feed.txt),
[MD5](https://threatview.io/Downloads/MD5-HASH-ALL.txt).
Они дают несколько типов IoC в формате «одно значение на строку».
MD5 добавляет файловый уровень обнаружения, хотя не заменяет более полные
базы образцов и анализ поведения файлов.

[Поставщик](https://threatview.io/) публикует бесплатные community-фиды
с ежедневным обновлением и агрегирует данные из разных открытых источников.
Это расширяет охват, но ограничивает прозрачность происхождения отдельного IoC.
Ложные срабатывания не исключены; в TXT нет дат наблюдения и контекста каждой
записи. Дата обновления файла не доказывает свежесть всех его индикаторов.
Три файла считаются **одним источником** и заменяются в БД вместе,
только после успешной загрузки и разбора всех трёх.

### Blocklist.de

Используется [общая выгрузка IP](https://lists.blocklist.de/lists/all.txt).
По [описанию сервиса](https://www.blocklist.de/en/export.html), она содержит
адреса, сообщённые в связи с атаками на серверы за последние 48 часов,
и формируется каждые 30 минут. Это дополнение для проверки входящих соединений,
подбора паролей и атак на опубликованные службы.

Источник добавляет сведения об атаках на серверные службы, а совпадения IP
с CINS Army и ThreatView демонстрируют повышение приоритета.
Список не специализирован на российском финансовом секторе.
Нахождение IP в нём также не доказывает, что за всеми
соединениями с адреса стоит один злоумышленник.

### Пересечения и ограничения приоритета

Совпадение типов не гарантирует совпадения значений в каждой загрузке.
ThreatView агрегирует чужие данные: совпадение между списками нельзя считать
доказательством независимости первичных наблюдений. Счётчик реализует
именно правило ТЗ. Повторы и несколько файлов поставщика его не увеличивают.

IPv4 встречается во всех трёх источниках: одинаковый адрес из одного списка
получает Medium, из двух — High, из трёх — Critical. Каждый такой результат
содержит названия источников; их состояние доступно в JSON и `--stats`.
Демо воспроизводит все три уровня на документационных адресах.
Реальные тройные совпадения проверены сетевым сбором и приведены в
[примере запуска](examples/live_run.md). Их число меняется вместе с выгрузками.

Для промышленного применения в финансовой компании в РФ предпочтительнее
использовать источники с отраслевым контекстом и регулярной поставкой данных, например
[ФинЦЕРТ Банка России](https://www.cbr.ru/information_security/fincert/),
[BI.ZONE Threat Intelligence](https://bi.zone/catalog/products/threat-intelligence/)
и [Kaspersky Threat Data Feeds](https://www.kaspersky.ru/enterprise-security/threat-data-feeds).
Однако они требуют организационного подключения или корпоративной подписки.
Поэтому в тестовом задании выбраны публичные бесплатные выгрузки без ключей,
чтобы проверяющий мог сразу запустить программу.

## Команды, вывод и экспорт

Для сбора достаточно запустить `collect.py` без параметров:

```shell
python collect.py
python ioc.py --stats
python ioc.py --level high --limit 20 --offset 0
python ioc.py --level medium --limit 0 --format json --output data/medium.json
python ioc.py --level high --format csv --output data/high.csv
python ioc.py --level medium --format txt --output data/medium.txt
```

Справка со всеми доступными параметрами вызывается через `--help`:

```shell
python collect.py --help
python ioc.py --help
```

`--level` принимает Critical, High, Medium без учёта регистра.
По умолчанию показываются первые 100 записей; `--limit 0` означает все.
JSON содержит также `source_details`: состояние и время успешного сбора
источников. CSV и таблица сохраняют типы; TXT содержит только значения, поэтому
для дальнейшей обработки смешанных типов предпочтительнее JSON/CSV.

Заголовки и строки таблицы имеют одинаковые ширины колонок; длинные значения
в интерактивном терминале переносятся внутри колонок. Для файлов и перенаправления
ширина не ограничивается размером окна. Для очень узких окон удобнее JSON/CSV.

`INFO` — обычная диагностика, а не ошибка. Строка `source/feed` описывает
конкретную загрузку, строка `source: OK` — итог источника. `values` — число
проверяемых значений IoC, `unique` —
число уникальных валидных IoC, `duplicates` — повторы, `invalid` — отклонённые
значения. Логи пишутся в stderr, результаты — в stdout.

Коды завершения сбора: **0** — все источники успешны; **2** — частичный успех;
**1** — все источники недоступны либо ошибка БД; **130** — прерывание.
У argparse код **2** также обозначает неверные аргументы команды.

## Нормализация

- Пробелы по краям удаляются; внутренние пробельные и управляющие символы
  отклоняются. Восстанавливаются разделители `[.]`, `(.)` и схемы `hxxp(s)`.
- IP проверяются стандартным `ipaddress`; IPv6 сжимается. Scoped IPv6 отклоняется.
- Домены приводятся к нижнему регистру и ASCII/IDNA, конечная точка удаляется.
  Поддомены не склеиваются с родительским доменом.
- URL сохраняет схему, путь, регистр пути, порядок параметров, escapes и fragment.
  Нормализуются схема/хост; стандартный порт удаляется, пустой путь становится
  `/`. URL не превращается в домен или IP.
- `ip_port` сохраняет порт; IPv6 записывается как `[адрес]:порт`.
  Пара адрес/порт и отдельный IP — разные индикаторы.
- Хеш проверяется по алфавиту и точной длине своего алгоритма, затем переводится
  в нижний регистр. Хеши разных алгоритмов не объединяются.

Ключ `UNIQUE(type,value)` исключает дубли, а ключ
`PRIMARY KEY(indicator_id,source_id)` исключает повторный учёт источника.
Проверяется синтаксис, а не вредоносность или глобальная маршрутизируемость IP.
Доменам не выполняются DNS-запросы, переходов по IoC нет.
Встроенный IDNA-кодек Python реализует IDNA 2003.

## SQLite и повторный сбор

Используется **простая локальная встраиваемая СУБД SQLite**. Разворачивать
отдельный сервер, устанавливать PostgreSQL/MySQL, поднимать службу или контейнер
не требуется. SQLite — полноценная СУБД с SQL, индексами и транзакциями, но
работает библиотекой внутри процесса Python.

В обычной поставке Python уже доступны модуль `sqlite3` и библиотека SQLite.
Для используемых вычисляемых столбцов требуется SQLite **3.31+**.
`sqlite3.connect(...)` создаёт файл, SQL из `SCHEMA` в
`ioc_collector/database.py` создаёт таблицы и индексы. Исходники SQLite скачивать
и компилировать не нужно. Создание пустой структуры быстрое; основное время
занимает загрузка и запись индикаторов. Для нескольких параллельных писателей
архитектуру следует пересмотреть: [рекомендации SQLite](https://www.sqlite.org/whentouse.html).

Таблицы: `indicators` — IoC и приоритет; `observations` — связи с источниками;
`sources` — состояние сбора; `metadata` — служебные параметры и режим demo/live.
`level` — хранимая вычисляемая колонка, зависящая от `source_count`.

Каждый успешный сбор атомарно заменяет снимок одного источника:
добавляет новые связи, удаляет исчезнувшие, пересчитывает приоритет и удаляет
IoC без источников. Повторы внутри источника не повышают приоритет.
Ошибка загрузки или формата сохраняет предыдущий успешный снимок.

Снимок соответствует текущей выгрузке поставщика. Исчезновение записи
из неё **не означает, что индикатор стал безопасным**.
Приложение хранит последние успешные снимки источников.

`first_seen`, `last_seen` и `updated_at` — времена локальной обработки в UTC,
не даты активности угрозы у поставщика. История удалённых связей, контекст
кампаний и отдельный TTL пока не реализованы. При длительном сбое сохранённые
данные могут устареть; CLI предупреждает, `--stats` показывает `last_success`.

Рабочие БД, резервные копии и `.env` исключены из Git.

## Надёжность и проверка

HTTPS и проверка TLS включены. Перенаправления разрешены только в пределах
того же HTTPS-сервера. Временные сетевые ошибки и HTTP 408/429/5xx
повторяются ограниченно; учитывается `Retry-After`, максимум 30 секунд.
По умолчанию два повтора. `--timeout` ограничивает ожидание сокета,
а не суммарное время сбора.

Размер ответа ограничен 32 МиБ. Несовместимый формат, HTML вместо фида,
обрыв загрузки и более 10% невалидных значений отклоняются.
Пустой ответ считается подозрительным и сохраняет прежний снимок.

```shell
python -m unittest discover -s tests -v
```

Тесты не требуют сети и ключей. Проверяются форматы трёх источников,
нормализация, пересечения, все уровни приоритета, частичные ошибки, сохранение
снимков, запуск без секретов, согласованность связей в БД,
HTTP-повторы и запуск CLI.

Примеры: `examples/demo_run.txt`, `examples/live_run.md`,
`examples/live_stats.json`. Сетевой пример явно указывает, какие источники
проверены, и содержит фактическую статистику загрузки.
Ответы на вопросы ТЗ: [ANSWERS.md](ANSWERS.md).

```text
collect.py                  Сбор
ioc.py                      Запросы и экспорт
ioc_collector/sources.py     Публичные адреса и форматы источников
ioc_collector/feeds.py       HTTPS, повторы, разбор текстовых списков
ioc_collector/normalize.py   Нормализация типов IoC
ioc_collector/database.py    SQLite и транзакции
ioc_collector/collector.py   Независимая обработка источников
ioc_collector/cli.py         Команды и вывод
examples/                   Синтетические данные и примеры запусков
tests/                      Проверки без сети
```
