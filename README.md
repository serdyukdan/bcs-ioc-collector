# Сбор и приоритизация общедоступных IoC

Решение тестового задания для БКС на Python. Две консольные команды собирают
индикаторы из трёх открытых источников, сохраняют их в SQLite и выводят по
приоритету. Совпадение определяется по паре **тип + нормализованное значение**.

| Различных источников | Уровень |
| --- | --- |
| 3 | Critical |
| 2 | High |
| 1 | Medium |

Поддерживаются IPv4, IPv6 и домены. Это типы, которые предоставляют выбранные
фиды. URL, хеши, подсети CIDR и пары IP:port не преобразуются в IP или домены:
для них потребовались бы отдельные типы и правила сопоставления.

## Быстрый запуск

Нужны **Python 3.10+** и SQLite **3.31+** в стандартном модуле `sqlite3`.
В проверенном окружении использовался Python 3.12. Сторонних библиотек нет,
поэтому устанавливать пакеты через pip не нужно. `requirements.txt` приложен
для явного указания этого факта.

Для хранения используется **локальная встраиваемая СУБД SQLite**. Разворачивать
отдельный сервер БД, устанавливать PostgreSQL/MySQL или запускать контейнер
не требуется: программа сама создаёт файл базы и таблицы при первом сборе.
Это простое решение для одного компьютера и ручного консольного запуска.

Распакуйте проект и откройте терминал в каталоге `bcs-ioc-collector`.
В командах ниже `python` — установленный Python 3; на Linux он может называться
`python3`, на Windows можно использовать `py -3`.

```shell
python --version
python collect.py
python ioc.py --level critical
python ioc.py --level high
python ioc.py --level medium
```

База появится в `data/iocs.sqlite3`. Пути к БД и файлам экспорта отсчитываются
от текущего рабочего каталога. Регистрация и API-ключи не нужны. Для обычного
сбора требуется HTTPS-доступ к трём поставщикам; адреса фидов заданы в
`ioc_collector/sources.py`. Проверка TLS-сертификатов включена.

Сначала можно проверить всё без интернета:

```shell
python collect.py --demo
python ioc.py --db data/demo.sqlite3 --level critical
python ioc.py --db data/demo.sqlite3 --level high
python ioc.py --db data/demo.sqlite3 --level medium
```

Демо использует явно обозначенные синтетические данные из `examples/feeds`:
документационные IP-диапазоны и домены `.example`/`.test`. Ожидаемый результат:
**7 IoC, из них 1 Critical, 2 High, 4 Medium**. Режимы demo/live закрепляются в
метаданных БД; смешать их в одном файле программа не позволит.

## Почему выбраны эти источники

Выбор сделан для воспроизводимого выполнения тестового задания: три бесплатных
источника, автоматический сбор и запуск на компьютере проверяющего без выдачи
ему личных ключей кандидата. ТЗ допускает настройку ключей; доступ без регистрации
выбран как дополнительное удобство проверки, а не как обязательное требование.
Региональное и отраслевое покрытие этих источников для БКС отдельно не
подтверждено; приведённые ниже ограничения являются частью обоснования выбора.

| Источник | Что загружается | Назначение и ограничение |
| --- | --- | --- |
| [Blocklist.de](https://www.blocklist.de/en/export.html) | IP из `all.txt` | Адреса из сообщений об атаках за последние 48 часов по описанию поставщика. Полезны для проверки сетевой активности; список не устанавливает связь с атаками на российский финансовый сектор. |
| [CINS Army](https://cinsscore.com/) | IP из `ci-badguys.txt` | Дополнительные сетевые индикаторы из CINS, отобранные по активности на сенсорах и репутационным признакам. Российская отраслевая специализация не заявляется как критерий отбора в этом проекте. |
| [ThreatView](https://threatview.io/) | IP и домены из двух Community Feeds | Расширяет типы индикаторов и даёт третий список IP. Агрегирует несколько каналов; наличие в нём IoC не доказывает независимое подтверждение или применимость к БКС. |

Прямые адреса:

- Blocklist.de: <https://lists.blocklist.de/lists/all.txt>
- CINS Army: <https://cinsscore.com/list/ci-badguys.txt>
- ThreatView IP: <https://threatview.io/Downloads/IP-High-Confidence-Feed.txt>
- ThreatView domains: <https://threatview.io/Downloads/DOMAIN-High-Confidence-Feed.txt>

Это **три источника и четыре файла**: оба файла ThreatView относятся к одному
поставщику и не увеличивают число подтверждений сами по себе. IP намеренно
присутствуют у всех трёх поставщиков, чтобы уровни High/Critical могли возникать
на реальных данных. Домены расширяют покрытие; в текущей конфигурации они могут
иметь только Medium, поскольку доменный фид есть только у ThreatView.

Количество поставщиков не равно количеству независимых первичных наблюдений:
поставщики могут использовать общие upstream-данные, а ThreatView прямо
описывает агрегацию нескольких каналов. Здесь приоритет означает именно число
выбранных источников по ТЗ, а не доказанную степень опасности индикатора.

Все четыре файла доступны напрямую по HTTPS без регистрации и секретов.
Их строковый формат позволяет надёжно проверить сбор, дедупликацию, обновление
снимков и обработку сбоев. Проверяющий может сразу выполнить сетевой сбор
по приведённым командам.
На другом компьютере потребуются Python и сетевой доступ к адресам фидов;
отсутствие ключей само по себе не гарантирует доступность сайтов из любой сети.

### Применимость к БКС и российскому ландшафту угроз

Для российской финансовой организации такой набор даёт лишь общие сетевые
индикаторы. Для оценки целевых угроз нужны сведения о кампаниях против
российских организаций и финансового сектора, времени наблюдения, группировках,
тактиках и используемом ПО. В текущих фидах и схеме приоритизации этого контекста
нет. Поэтому решение демонстрирует механику ТЗ, но не заявляет достаточное
покрытие угроз БКС для промышленной эксплуатации.

Актуальность для России определяется целями и контекстом атаки. Фильтр по
российским IP или доменам `.ru` не заменяет такой анализ: управляющая
инфраструктура атакующих может находиться в других странах. Например,
[BI.ZONE описывает Vengeful Wolf](https://gti.bi.zone/) как кластер, атакующий
финансовые подразделения компаний и использующий серверы за пределами России.

публикаций одного поставщика не должно увеличивать число источников.

### Можно ли использовать ключ на другом компьютере

Сам по себе API-ключ не означает привязку к физическому компьютеру. Например,
официальный [Python SDK BI.ZONE](https://github.com/bi-zone/bizone-ti-lib)
настраивается адресом сервиса и `api_key`, а документация
[Kaspersky API](https://opentip.kaspersky.com/Help_ru/Doc_data/SubmitFileAPI.htm)
показывает передачу токена в HTTP-заголовке `x-api-key`.

Однако из этого не следует разрешение использовать один ключ на любом ПК:
должны подходить права учётной записи, условия доступа, квоты и сетевые
настройки. Публичные материалы, рассмотренные здесь, не дают универсальной
гарантии переносимости или отсутствия ограничений по исходному IP. Эти условия
нужно уточнять при получении доступа, а секрет передавать приложению через
окружение или хранилище секретов, не включая его в репозиторий.

Обоснование текущего выбора — **воспроизводимость без персональных и
корпоративных доступов**, простой автоматический сбор и проверяемое выполнение
ТЗ. Это компромисс с региональной релевантностью, а не утверждение о превосходстве
выбранных фидов. Для MVP в БКС следует оценить доступные организации каналы
ФинЦЕРТ, региональные TI-сервисы и открытые отчёты, проверить их покрытие
на корпоративных событиях и дополнить ими общие фиды. Наличие таких подписок
или доступов у самой БКС в рамках задания не проверялось.

## Команды и экспорт

```shell
# Свой файл БД, сетевой таймаут и число повторов после первой попытки
python collect.py --db data/custom.sqlite3 --timeout 20 --retries 2

# Общая статистика, типы IoC и состояние каждого источника
python ioc.py --stats

# По умолчанию показываются первые 100 строк; 0 означает все
python ioc.py --level High --limit 20 --offset 0
python ioc.py --level high --limit 0 --format json --output data/high.json
python ioc.py --level critical --limit 0 --format csv --output data/critical.csv
python ioc.py --level medium --limit 50 --format txt --output data/medium.txt

python collect.py --help
python ioc.py --help
```

Регистр названия уровня не важен. Табличный вывод выравнивает заголовки и
значения пробелами по общей ширине каждой колонки: значение, тип, число
источников, уровень, список источников, время обновления. В интерактивном
терминале длинные значения переносятся внутри своей колонки с учётом ширины
окна; для всех шести заголовков нужно не менее 58 символов. При записи в файл
или перенаправлении ширина определяется полным содержимым выбранных строк.
Сортировка стабильна: тип, затем значение; IP сортируются как строки.
JSON дополнительно содержит `source_details` с состоянием и временем последней
успешной загрузки каждого источника. CSV содержит все основные поля, TXT —
только значения. `--stats` всегда выводит JSON независимо от `--format`.
Диагностика идёт в stderr и не повреждает JSON/CSV в stdout.

Коды завершения сбора: `0` — все источники обработаны; `2` — частичный успех;
`1` — все источники недоступны либо ошибка БД/файла; `130` — прерывание Ctrl+C.
Запрос возвращает `0` и при пустом результате, `1` при ошибке БД/экспорта.
Ошибки аргументов у обеих команд возвращают `2`, как принято в `argparse`.

## Нормализация

- Пробелы по краям удаляются. `[.]` и `(.)` заменяются точкой.
- IPv4/IPv6 проверяются через `ipaddress`; IPv6 сжимается и переводится
  в нижний регистр. IPv4 с неоднозначными ведущими нулями отклоняется.
- Домены приводятся к нижнему регистру и ASCII через встроенный IDNA-кодек;
  одна конечная точка убирается. Проверяются длина имени и DNS-меток.
- Поддомены не объединяются с родительским доменом. Домены не резолвятся в IP.
  Никаких запросов к самим IoC программа не выполняет.
- Тип фида проверяется: адрес в доменном фиде не станет доменом.
- Пустые строки и строки-комментарии `#`, `;`, `//` пропускаются.
  Невалидные строки учитываются в статистике и отбрасываются.

Например, `192.0.2[.]10` и `192.0.2.10` — один IPv4; `BAD[.]EXAMPLE.` и
`bad.example` — один домен. `2001:0DB8:0:0:0:0:0:1` и `2001:db8::1` — один IPv6.
Уникальный индекс `(type, value)` и первичный ключ связи `(indicator_id,
source_id)` защищают от дублирования и повторного учёта одного источника.

Проверяется синтаксис, а не репутация, существование домена или глобальная
маршрутизируемость IP. Встроенный IDNA-кодек реализует IDNA 2003; для IDNA 2008
в промышленной версии нужна отдельная библиотека и согласованные правила.

## Хранение и повторный сбор

`indicators` хранит тип, значение, `source_count`, `level`, `first_seen` и
`updated_at`. `level` — хранимая вычисляемая колонка SQLite, зависящая от
`source_count`. `observations` связывает индикаторы с источниками и хранит
`first_seen`/`last_seen` связи. `sources` хранит состояние поставщика,
последнюю попытку, последнюю успешную загрузку и сообщение об ошибке.
`metadata` содержит версию схемы и режим данных.

SQLite — полноценная встраиваемая СУБД с SQL, индексами и транзакциями. Для
этого проекта она выбрана как простое локальное хранилище: работает библиотекой
внутри процесса Python, без отдельного сервера, службы и сетевого подключения
к БД. **Развёртывание серверной СУБД не требуется**: механизм управления базой
предоставляет библиотека SQLite.

В обычной поставке Python доступны стандартный модуль `sqlite3` и готовая
библиотека SQLite. При первом запуске
`sqlite3.connect(...)` создаёт файл базы, а `conn.executescript(SCHEMA)` выполняет
SQL-команды создания таблиц и индексов. Сама схема находится в переменной
`SCHEMA` в `ioc_collector/database.py`. Исходники движка SQLite скачивать и
компилировать не требуется. `CREATE TABLE IF NOT EXISTS` позволяет повторять
запуск без очистки существующих таблиц: структура создаётся быстро, основное
время занимает скачивание, проверка и запись самих индикаторов.

Такой выбор соответствует небольшому консольному приложению на одном
компьютере. Для множества параллельных писателей или общего сетевого сервиса
потребуется пересмотреть архитектуру хранения; эти границы также описаны в
[рекомендациях SQLite по применению](https://www.sqlite.org/whentouse.html).

База содержит **последний успешно загруженный снимок каждого источника**:

1. Скачиваются и проверяются все файлы одного поставщика.
2. В одной транзакции добавляются новые IoC и обновляются связи.
3. Исчезнувшие из успешного снимка связи удаляются. Приоритет пересчитывается
   и может понизиться. IoC без единого источника удаляется.
4. Транзакция фиксируется, после чего начинается следующий поставщик.

Состояние трёх источников не является синхронным снимком всего интернета:
каждый обновляется в своё время. Повторный сбор тех же данных сохраняет число
IoC, связи и уровни, обновляя время наблюдения. Все даты — UTC ISO 8601.
`updated_at` — время локальной успешной обработки IoC или изменения его
связей, а не дата обнаружения угрозы поставщиком. История удалённых IoC и
удалённых связей в этом небольшом решении не архивируется.

При сетевой ошибке прежний снимок сохраняется, поставщик получает статус
`error`, остальные обрабатываются дальше. В запросе появляется предупреждение
о потенциально устаревших данных; `--stats` показывает детали. Автоматического
TTL пока нет, поэтому длительный сбой требует внимания к `last_success`.

Для временных HTTP-ошибок и ошибок сети предусмотрены повторы с задержками
1 и 2 секунды по умолчанию; для 429 учитывается `Retry-After` с пределом
30 секунд. Таймаут относится к сетевым операциям, не ко всему запуску.
Один файл ограничен 32 МиБ. HTML, пустой фид, обрыв с несовпадающим
Content-Length или более 10% невалидных строк считаются ошибкой фида.
Порог 10% — защитная эвристика от смены формата. Если источник действительно
начнёт публиковать пустые списки, это решение нужно пересмотреть явно.
Сбой любого из двух файлов ThreatView сохраняет целиком его прежний снимок.

## Проверка

```shell
python -m unittest discover -s tests -v
```

Тесты не требуют сети. Проверяются нормализация, повторный учёт, все уровни,
понижение приоритета, удаление исчезнувших индикаторов, частичный сбой,
атомарность поставщика, откат транзакции, retries, HTTP 429, ошибочные ответы,
разделение demo/live и реальные вызовы CLI через subprocess.

Примеры выводов и результаты проверенного сетевого запуска находятся в
`examples/demo_run.txt`, `examples/live_run.md` и `examples/live_stats.json`.
Там зафиксирован один запуск: публичные фиды со временем меняются.
Краткие ответы на вопросы ТЗ — в `ANSWERS.md`.

## Структура проекта

```text
collect.py                   Команда сбора
ioc.py                       Команда запросов и экспорта
ioc_collector/sources.py     Три поставщика и их фиды
ioc_collector/feeds.py       HTTP, retries, разбор строк
ioc_collector/normalize.py   Нормализация IP и доменов
ioc_collector/database.py    Схема SQLite и транзакции
ioc_collector/collector.py   Обработка поставщиков
ioc_collector/cli.py         Аргументы и форматы вывода
tests/                       Автоматические тесты
examples/                    Демо и сохранённые результаты
ANSWERS.md                   Ответы на вопросы задания
```

Основной объём реализации — сбор, сопоставление и согласованное обновление
БД. Дополнительно сделаны обработка defanged-значений, retry, экспорт,
статистика, offline-демо и тесты. Постоянный сервис, планировщик и Docker для
ручного консольного запуска не требуются.
