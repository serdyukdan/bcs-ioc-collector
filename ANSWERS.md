# Ответы на вопросы тестового задания

## Почему выбраны именно эти три источника

Выбор обоснован требованием взять **3 бесплатных открытых источника**,
стремлением к широкому покрытию типов IoC и наличию пересечений для
демонстрации сопоставления и повышения приоритета. При полностью разных типах
у всех источников каждый индикатор всегда имел бы Medium — минимальный уровень
по ТЗ, а не Low.

Дополнительное условие — удобство проверяющего: **полный сетевой сбор без
регистрации, API-ключей и настройки секретов**, а не только офлайн-демо.

- **PhishTank:** подтверждённые действующие фишинговые URL для почты и веб-трафика.
- **ThreatView:** IP, домены и MD5 — сетевой и файловый уровни обнаружения.
- **Blocklist.de:** IP, замеченные в атаках на серверные службы.

ThreatView и Blocklist.de пересекаются по IP. Три файла ThreatView считаются
одним источником. Совпадения агрегированных списков не доказывают независимость
первичных наблюдений. Общего типа у всех трёх нет, поэтому Critical проверяется
отдельным тестом на условных источниках; реальные форматы не искажаются.

Это компромисс для воспроизводимой проверки, а не обещание максимальной защиты
БКС. У PhishTank ограничено число анонимных загрузок; у текстовых списков
недостаточно контекста и дат отдельных IoC. Подробности и официальные ссылки
приведены в [README](README.md).

Для промышленного сервера я бы начал с пилота **ФинЦЕРТ, BI.ZONE TI и Kaspersky
Threat Data Feeds**: отраслевой обмен, российский ландшафт угроз и регулярные
структурированные потоки соответственно. Они требуют организационного
подключения или согласованных корпоративных условий. Наличие доступа у БКС
не предполагается. Итоговый набор определяется полезностью на телеметрии,
свежестью и ложными срабатываниями, а не страной поставщика.
Секреты в промышленной системе хранятся вне Git. Статьи Securelist полезны
для контекста расследований, но не заменяют регулярные фиды.

## Как нормализуются и сопоставляются IoC

Сопоставление строгое: `(type, normalized_value)`.
IP проверяются через `ipaddress`, IPv6 сжимается. Домены приводятся к
нижнему регистру и ASCII/IDNA. Восстанавливаются defanged-разделители.

У URL нормализуются схема и хост, убирается стандартный порт; путь, его регистр,
порядок параметров и fragment сохраняются. IP:port сохраняет порт.
Хеши проверяются по длине алгоритма и переводятся в нижний регистр.
URL не превращается автоматически в домен, а IP:port — в отдельный IP:
это расширило бы область блокировки и создало искусственные совпадения.

Уникальные ограничения БД исключают дубли индикаторов и повторный учёт одного
источника. Разные алгоритмы хеширования остаются разными типами IoC.

## Как добавить четвёртый источник

Добавить `Source` с уникальным идентификатором и один или несколько `Feed`
в `SOURCES`. Для поддерживаемого формата достаточно описания запроса;
для нового формата нужен парсер в `feeds.py`, а для нового типа —
нормализация и миграция ограничения `indicators.type`.
Добавляются синтетическая выгрузка и тесты, включая ошибки источника.

Текущая конфигурация использует публичные GET-запросы. Для будущего API
с авторизацией понадобится адаптер, читающий секрет из окружения или хранилища
секретов; ключ нельзя включать в исходники, тестовые данные и логи.

Общий сбор и БД уже обрабатывают произвольное число источников.
Отдельно нужно определить политику приоритета: сейчас три и более —
Critical, два — High, один — Medium. Если для четырёх источников Critical
должен означать именно четыре, понадобится изменение вычисляемой колонки
и правила для трёх подтверждений.

## Что произойдёт при недоступности одного источника

Ограниченные повторы выполняются для временных сетевых ошибок. После
исчерпания попыток прежний снимок остаётся, источник получает статус error,
остальные продолжают обрабатываться. Отказ одной из трёх выгрузок ThreatView
сохраняет весь прежний снимок этого поставщика.

Частичный успех даёт код 2; полная неудача — 1. `ioc.py` предупреждает
о старом снимке, `--stats` показывает время последней успешной загрузки.
Успешное восстановление заменяет снимок и снимает ошибку.
Ошибка локальной БД останавливает запуск; транзакция источника откатывается.

Пустой или повреждённый ответ не очищает БД. Перед миграцией схемы или
удалением прежних источников создаётся резервная копия; ошибка копирования
останавливает изменение. Удалённые из конфигурации источники перестают
участвовать в подсчёте приоритета.

## Что изменить для MVP

Сначала согласовать актуальность индикаторов и правила использования:
приоритет ТЗ, уверенность поставщика и решение об автоблокировке — разные вещи.
Нужно учитывать зависимость источников и стоимость ложной блокировки рабочего
сервиса. Разным типам IoC нужны соответствующие средства обнаружения.

Сейчас сохраняются последние успешные выгрузки поставщиков. Для промышленного
решения нужны инкрементальные обновления, история и TTL по типам. Исчезновение
записи из выгрузки не означает её безопасность.
Нужно сохранять даты наблюдений у поставщика и контекст кампании; сейчас
времена в БД относятся к локальной обработке.

Для БКС нужно оценить региональное и отраслевое покрытие на телеметрии,
проверить доступные организации каналы ФинЦЕРТ и TI-сервисы. Доступ к ним
не предполагается обязательным для проверки тестового.

Затем добавить планировщик, контроль параллельных запусков, мониторинг
длительных сбоев, allowlist, условные HTTP-запросы и согласованные лимиты.
Большие выгрузки и экспорт стоит обрабатывать потоково; сейчас они
материализуются в памяти. Лицензии и условия API нужно перепроверять.

SQLite достаточна для небольшого локального приложения: не нужны отдельный
сервер БД, установка серверной СУБД или компиляция исходников.
При частых параллельных записях и работе нескольких пользователей можно
перейти на PostgreSQL и добавить API с авторизацией.
